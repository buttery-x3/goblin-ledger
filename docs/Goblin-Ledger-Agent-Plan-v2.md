# Goblin Ledger — agent development plan

**Reviewed edition · 19 November 2026**  
**Product contract** [Dashboard design v2](Goblin-Ledger-Design-v2.md)  
**Local checkout** `D:\dev\goblin-ledger` · **Public remote** [buttery-x3/goblin-ledger](https://github.com/buttery-x3/goblin-ledger) · **Integration** `development` · **Approved milestones** `main`

## Lead-agent hand-off

> Build the local Windows web application in the companion design. Work in feature branches. Delegate independent work to sub-agents in separate worktrees and assign a different agent to review each branch. Own tests, review fixes, integration, the Windows launch path and milestone reporting. Merge reviewed work into development as it becomes ready. Take each milestone through its automated acceptance checks without routine user intervention.
>
> Use shell, Git/GitHub, HTTP, file operations, simulated-DOM component tests and a Lua harness. No computer control, desktop or browser driving, game client automation, screenshots obtained by UI automation, or simulated player input. Exercise the installer only against temporary installations during development. The real user selects Install in Settings.
>
> Cut milestone candidates from integrated development. Main requires the user’s explicit approval for the named candidate and commit. Continue the next milestone on its branches while approval is pending. Keep live-provider, fixture, visual and in-game verification accurately labelled. The user’s private data stays on their machine.

## 1. Start and divide the work

```powershell
Set-Location -LiteralPath 'D:\dev\goblin-ledger'
git rev-parse --show-toplevel
git remote get-url origin
git status --short --branch
git branch --all
gh auth status
```

Read the repository’s instructions and README. Verify the checkout and remote owner/name, preserve uncommitted user work, fetch origin and identify the actual base commits. Reuse remote `development` if present. Otherwise create it from `origin/main` and publish that integration ref. Create a sibling worktree if the player’s checkout is busy. Keep the two v2 files together under `docs/` on the bootstrap feature branch. Use `AGENTS.md` for the short, durable operating rules. Here “M0–M5” refers to delivery milestones, not new services.

| Owner | Write boundary | Contract with other lanes |
|---|---|---|
| Lead / integration | Workspace manifests, lockfile, migrations sequence, API contracts, CI, Windows start, review ledger | Freeze shared schemas before parallel writers depend on them. One owner reconciles migration numbers and lockfile changes. |
| Workspace / Atlas | Layout manager, panel registry, SVG geography, navigation, shared chart/table components | Consumes route IDs, geometry coordinate spaces, selection policy and evidence envelopes. Never selects a farm by item name. |
| Data / economics | Source adapters, snapshot pipeline, graph and quote queries, deterministic opportunity rules | Returns source, house, version, coverage, evidence and units. Exposes missing capabilities to the UI. |
| Personal data / addon | Lua event capture, installer, import, Characters and Positions data | Owns the versioned addon export and synthetic fixtures. Interface/build, inventory completeness and receipt identity are explicit. |
| Independent reviewer | Reads diff and surroundings, runs acceptance checks in a separate worktree | Reviews a commit it did not author. Delivers findings with severity and test evidence, then revisits fixes. |

Use fewer lanes for a narrow change. Assign each new feature a slice of its UI, data and tests; agree file ownership before editing a shared pane. When a lane blocks on external data, continue its fixture implementation and independent work, recording exactly what is still unobserved.

## 2. M0 technical decisions

|---|---|
| Toolchain | Baseline checked on 19 November: Node **26 LTS** (26.13.1 release checked), React **19.3**, Vite **8.3** stable line, TypeScript **7.0.2** stable release inspected, Fastify **5.x**. Resolve the newest mutually compatible stable versions at bootstrap using official release notes, registry dist-tags, engines and peer ranges. Pin Node, pnpm and dependencies, commit a lockfile and use frozen installs in CI. “Latest” in the docs is a selection procedure, never a floating production dependency. | SQLite on Windows | First try a maintained stable `better-sqlite3` release with a prebuilt binary for the chosen Windows x64/Node ABI. If the native driver fails, select a supported stable version pair or document and test a built-in-driver exception; keep this choice behind the small persistence boundary. [Driver releases](https://github.com/WiseLibs/better-sqlite3/releases) · [Node SQLite status](https://nodejs.org/download/release/v26.13.1/docs/api/sqlite.html) · [SQLite backup](https://sqlite.org/backup.html) |
| UI | FlexLayout React stores tabs/splits as a serialisable model. Keep view-specific filters and selections in a versioned app record keyed by pane instance ID. React Query shares fetched data across panes. TanStack Table handles sorting; use row virtualisation or bounded paging for large tables. ECharts renders series and SVG renders the Atlas. Keep density, colours, legends and saved presets customisable. [FlexLayout API](https://github.com/caplin/FlexLayout) |
| Local runtime | A Fastify service serves its own built frontend and same-origin typed endpoints. One background runner owns schedules, bounded queues and SSE. Use one DB writer, batch snapshot writes and keep blocking imports off the HTTP event loop. No separate infrastructure installation for the player. Distinct CLI dev/build/start/check/test commands are useful to agents. |
| Windows launch | Ship a repeatable clean-checkout setup/build command and a one-action `Start-GoblinLedger.cmd` for subsequent use. Resolve paths relative to the launcher, check dependencies, reuse a healthy running instance and present its URL. Surface startup errors in a readable local diagnostic if HTTP startup fails. Keep production startup independent of the Vite dev server. |
| Public/private boundary | Keep DB/WAL, logs, backups, secrets, raw exports, article caches and machine-specific config under the local user profile. Store secrets using the Windows user credential store or user-scoped DPAPI. Publish original code/geometry, source links, synthetic examples and sanitised checks. Real acquisitions, character names and raw provider responses are unsuitable public fixtures. [Windows DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) |

**Monorepo shape.** `apps/web` owns the frontend; `apps/local` owns the service, adapters, jobs and DB migrations; `packages/domain` owns shared schemas, economic calculations and IDs; `addon/GoblinLedger` owns the bundled Lua addon. Keep tests close to code and shared fixtures under `fixtures/`. Start with modules inside these boundaries. A new rule declares its inputs and explanation, a panel declares its renderer and saved-state schema, and a source adapter declares supported fields, cadence and retention.

**Small shared contracts.** A published observation needs a house and provider ID, source timestamp, retrieval time, source method/build and field-level availability. Add the book timestamp and truncation to depth quotes. A route has a stable ID and map/floor coordinate space. An opportunity references the responsible rule version, evidence and scope. Physical stock, acquisition lots, recognised receipts and reconciliation are separate records. Use integer copper with correct whole-settlement rounding. Protect multiplication/aggregation against JS precision loss, encoding large integer totals explicitly at JSON boundaries. Time is UTC in storage and local in the UI. Bind all local endpoint paths under `/api/v1`.

**Prior implementations worth checking.** Simsar demonstrates a small export addon feeding a local dashboard. The open-source WoW Forever AH scanner has separate collectors for static recipes and market snapshots. Inspect their actual contracts and tests before reimplementing a parser or normaliser. Check the licences for code and any bundled game data separately. Goblin Ledger still needs its own linked viewports, wall evidence, source policies and position accounting. [Simsar](https://github.com/berkecuhadar/simsar-forever) · [WoW Forever AH scanner](https://github.com/petersutarik/wow-forever-ah)

## 3. Prove external inputs before depending on them

**Do the contract probe in M0, ahead of the full M1 pipeline.** Use the selected home region in the real app. A smoke run may use a clearly labelled US fixture/diagnostic profile while region is unconfigured. Discover the market and check that group, faction, currency units and observation times agree before selecting its key. Record a sanitised local probe summary. A populated HTML page or an API health response cannot mark a price adapter as live-verified.

| Capability | Probe and consequence |
|---|---|
| Market discovery and bulk | GET `https://auctionhouse.tk.gg/api/markets`. Select one matching region/PvP group/Alliance record. GET `/api/m/{key}`, resolve `f` column names for `items[].o`, check `house`, `t`, `sell`, `ask`, `ask2`, `listed`, `depth5`, `nc`, `flowHours` and nullable 24-hour metrics. Handle an empty pre-first-snapshot response. Where a provider infers market labels, record the mapping basis and cross-check several like-for-like items against separately identified observations. If calibration remains provisional show the reason. |
| History and exact tiers | Fetch a listed item via `/api/m/{key}/item/{id}?hours=24`, preferring 18945 when present. Validate `series.t`, aligned stats, `method.since`, `bookT`, `bookMore` and rows of price/units/auctions. A requested item absent today is a legitimate result. An explicit cache-version URL is not a guarantee that an earlier price ladder can be retrieved. At most one overview poll per market per hour, or fetch on a genuinely new provider snapshot event. Fetch item detail serially from a bounded priority queue, reusing the cache across panes; never crawl every item endpoint. [Primary API](https://auctionhouse.tk.gg/data/) |
| Static catalog | Fetch bulk `/api/recipes` once, verify a real product link, reagent quantities, null output handling and vendor-price semantics. Refresh on supported revision/cadence. For optional ForeverDB.net probe `/api/v1/meta`, a profession detail record, `/merchants-favor`, `/gathering/{slug}`, builds and changes-seen under the v1 prefix. Check attribution, pagination, limited stock, quantities per purchase, random-output range and observed-vs-inherited fields. Use an identifying User-Agent and locally configured key. Respect 402/403/429 distinctions and Retry-After. [ForeverDB.net docs](https://foreverdb.net/developers) |
| Independent/fallback coverage | An attributed AHledger `/v1/prices/{market}/{id}` response or price table may corroborate a price and supply, at its own scan time. Its separate house code, missing volumes, licensing and cache rules travel with the response. Cache-limited data remains outside durable raw/derived archives and backups. Missing exact tiers disable wall-depth and batch-quote claims for that source. A verified direct Blizzard adapter can deliver current listings when configured; it does not magically supply past sold volume. [AHledger docs and policy dates](https://ahledger.com/developers) · [Direct listing vs commodity routes](https://github.com/cnanas/Wow-Forever-Auction) |
| World and article evidence | Verify at least one named outdoor route, one instance, a usable geographic anchor and one dated source with specific advice. A source may document a route while leaving yield unknown. Use original geometry plus cited sources where reusable geometry is unavailable. Demonstrate the capability with a real accepted source; exercise denial, empty feed and missing publication date as separate cases. [Skulk Rock guide](https://www.icy-veins.com/wow-forever/herbalism-leveling-guide) · [Map frames and provenance](https://wowforevertierlist.com/zones/map) |

**Three distinct test results.** *Fixture pass* proves logic. *Live verified* requires a real successful request, validated content and a recorded observation time for that capability. *Blocked / degraded* proves the app knows what is unavailable. A failure-path pass permits integrating reviewed code on `development`; report the live exit criterion as outstanding and retry via a permitted source or access path. Keep unrelated milestones moving. A user may approve a clearly described reduced milestone. Never silently turn that exception into the scope of the finished product.

## 4. Milestones and acceptance

### M0 · Start the app, arrange it, see it working

Lead implements the production launcher, DB migration path, job registry, bootstrap diagnostics, log history and Console. Workspace agent implements all four presets, state persistence and a working two-route demo with a full-height vector map. Data agent can probe external contracts independently. Integrate a vertical slice from typed HTTP to frontend action before expanding the panel catalog.

**Exit.** A clean Windows profile can start the production build with documented commands. The local smoke fetches the shell/assets, health and real service endpoints. The 1+3 arrangement restores after restart. Clicking either of two same-herb/same-zone routes selects its own farm and preserves the world-wide Opportunities pane. A failed demo job appears in Console and a retry has a new run/attempt identity. Demo storage is isolated; an unavailable live source never substitutes fake prices.

### M1 · Collect a house and discover peculiarities

Data lane ingests bulk snapshots, selected detail, nullable flows and the recipe catalog. Economics lane implements the general vendor-floor scanner, supply shocks, sparse BoE lookup, method-aware charts and quantity-sensitive details. Discover candidates from the house before reading personal watches. Store observations atomically and publish an analysis keyed to its input snapshot.

**Exit.** With a source-verified coherent snapshot, the player can search a real house, see the as-of time and drill into a real item. Independently, fixture tests establish that the scanner finds a new, unwatched item at 0% price change, rejects a one-unit bait listing as a concentrated wall, and requires three appropriately ordered observations for a down/up refill. Changing item IDs in the fixtures leaves the rule valid. M1 remains explicitly partial if these logic checks pass but market payloads are unavailable.

### M2 · Compare an outing, a craft and an unlock

World lane implements route editing and timed run/haul entry, zone/instance geometry and comparable return overlays. Ship a searchable starter catalog with at least two distinct gather routes for one output and one solo-instance loop, each with its own requirements, sources and precision. Skulk Rock and Jintha’Alor in the Hinterlands are sourced candidates for separate outdoor/cave records, with Maraudon as an instanced alternative. Verify access and geometry precision separately from guide-reported yields. The same-zone geometry case also exists as a controlled fixture. [Route descriptions](https://afleurdenet.com/where-to-find-blindweed-and-ghost-mushroom-in-wow-forever-2026-farming-guide/) Link old or sparse routes to their evidence and expose missing yield. Game-data lane implements recipe/quest/vendor relationships, alternative crate fills, writ gates, cross-profession uses and actual-quantity quotes.

**Exit.** Change the price, yield, travel time or available character and see which route wins for a fixed play session. A lack of measurements gives an explicit data gap and usable break-even yield. The Mender’s Potion fixture flips from profitable to loss-making as volume increases. A quest branch consumes its input once and respects bound outputs. Account for shared reagents across alternatives so several crafts cannot all buy the same cheapest units. Graph traversal handles cycles, mutually exclusive rewards and exhausted stock. No route-specific hardcoding of the design’s demonstration items.

### M3 · Install the addon and value the player’s holdings

Addon lane implements event-based capture and a build-capability table for class/XP, bags, bank, profession visibility, money, binding and variants. Keep data acquisition silent. Integration lane implements folder selection, addon staging/update, export parser/watcher, Characters, Positions and manual transaction entry. Test optional invoice capture against compatible data before enabling it; manual entries provide cost basis without mailbox access.

**Exit.** From Settings, a player can pick a WoW parent or product root, verify the destination, install/update and see why character or bank data is waiting. Fixture exports from two alts produce correct distinct login, bank, inventory and position results. A natural, existing real export, if available, can validate the parser locally without publishing personal data. Record separately whether a real Forever client has been observed executing **this** addon build. An install test on a synthetic tree cannot establish that.

### M4 · Track where guide readers go and which alt can act

Research lane implements permitted intake, canonical URL/revision handling, changed-use events, article markers and optional AI annotations. Progression lane applies verified account-level challenge completion and per-character perks, plus profession/recipe eligibility and links to the farm, craft or market the unlock enables.

**Exit.** Show one real source that names a route, its actual advice and original link. No reach or saturation estimate appears without corresponding evidence. A second source of the same herb remains discoverable. Editing an article updates its revision without creating another independent endorsement. A build change or observed turn-in updates affected item theses. A level-24 character can be one level from a milestone with **new point**, **already earned** or **completion unknown** outcomes as appropriate. A skill-123 Alchemist is seven points short of learning the example recipe even if the profession’s account Legacy challenge has already been earned.

### M5 · Candidate ready for the player

Run the release artifact from a clean path and ordinary Windows user profile. Verify first launch, upgrade, DB backup/restore, preserved layouts, receipts and lots, real source capability status, disconnect/reconnect and simulated sleep/resume. Supply a short README for first launch, addon setup, original data sources and Console recovery. Confirm every production pane has its real data path and each backend script can be found in Status / Console.

**Exit.** Present integrated commit, candidate PR, exact launch instructions, independent review, automated results, live/source coverage and client/visual gaps. Explicitly identify any remaining item that changes a product promise. A polished demo with a failed market probe does not satisfy the live gold-making release.

**Parallel schedule.** After the M0 schema/fixture contracts land, M1 sources, M2 world content and M3 addon/export work have independent lanes. M4 research fixtures and date handling can start before personal data is ready. Prepare these in branches while an earlier milestone integrates. Capture an exact integration commit for the earlier milestone **before** merging later, unrelated feature work beyond its declared release scope.

## 5. Implementation details that matter during unattended work

**Catalog, history and load.** Index observations by provider, house, item/variant resolution and source time. Index relationship edges by both input and output. Separate the latest published snapshot pointer from staged fetches/analysis so a retry or crash cannot blend timestamps. Retain null flow fields and method transitions, and distinguish observed zero listings from no valid snapshot. Keep raw data according to the provider’s policy. An illustrative 6,600 items × 24 observations × 30 days gives **4,752,000 item-hours**. Generate a synthetic data set at this order of magnitude for a local benchmark. Use a bulk sweep, small bounded detail cache, indexed pagination and measured retention. Record disk size, timings and memory for ingest, dashboard open and one item drill-down on the reference machine. Keep heavy benchmarks out of every small PR.

**Installer.** Service-backed directory listing and paste-path validation run under the current Windows user. Record candidate product/build, ownership manifest, recent import and last error. Install files beneath the canonical selected Forever addon root only. Recheck reparse/junction targets before mutation. Stage on the same volume, validate the staged manifest, retain the previous owned version, and journal swaps so the next start can recover from an interrupted Windows rename. Unknown files or another addon at the target produce a safe conflict. Preserve WTF/SavedVariables and other addons on update. A directory with identical bytes is already installed. Permissions errors provide an actionable message in Settings; scanning never installs automatically.

**Export and ledger.** Import only the selected account’s Ledger export, with bounded file size and a restricted non-executing parser for SavedVariables table literals. Store schema/build and per-scope completeness plus sequence/time. Combine directory watching with a startup/resume/file-change rescan. Windows can miss watch events after directory moves; watch the enclosing directory and handle atomic replacement. Parse into a transaction after the file settles. A content hash alone deduplicates re-import of the *same file*, but repeated cumulative exports also require event IDs and per-scope ordering. A parse failure, missing file or stale scope leaves earlier good observations intact. Rebuild projections deterministically from known lots/receipts and physical snapshots. [Node filesystem caveats](https://nodejs.org/api/fs.html) · [Existing local dashboard and exporter](https://github.com/berkecuhadar/simsar-forever) · [Forever bank completeness handling](https://github.com/drockzoids-wow/WoW-Forever-Suite/blob/main/src/WoWForeverSuite/Inventory.lua)

**Jobs and diagnostics.** Keep immutable attempt IDs plus logical idempotency keys, e.g. adapter + house + source revision for snapshot publication. Persist a lease/heartbeat, progress, last-success cursor and terminal outcome. One worker owns a given logical job at a time. A retry is a new attempt of the same work. Handle no-change, partial, failed, paused, interrupted and successful outcomes. Respect provider backoff, caps and conditional requests; stop automatic retry on invalid credentials. After downtime do one bounded catch-up, never invent missed ladders or put an old achievement/quest under today’s timestamp. For historical corrections preserve a revision and its evidence.

**Front-end visibility.** Register every runtime process, watcher, import, source poll, analysis pass, article fetch/summary and addon operation. Capture structured logs plus child stdout/stderr with the run ID, stage, counts, error, exit code and next action. Provide list/history, details/log pagination, SSE and typed run/retry/pause controls. Keep one live event stream for all viewports; after a retention gap, re-fetch the current state. Bound retention and redact keys, tokens, account names and sensitive paths before persistence or export. Report a service disconnect in the frontend; bootstrap failures must remain readable from the launcher even when the API never started.

**Local network boundary.** Bind to loopback; validate intended Host/Origin and protect state-changing requests with a same-origin session. Limit folder browsing to directory selection and named installation operations. Serve no arbitrary files or shell. Fetch articles from configured public sources with time/size limits and redirect validation. Keep the explicitly configured local AI endpoint a separate adapter. Send article content as untrusted data, validate model output against known entities and keep all write authority in application code.

**Recovery.** Keep schema versioning for database, layouts and addon exports independent. Back up with SQLite’s online backup facility or a quiesced consistent snapshot before migration. A lone copy of the main DB file from a live WAL database can omit committed data. Restore into a temporary profile, run integrity and migration checks, reapply expiry and prove that lots, notes and layouts survive. [SQLite online backup](https://sqlite.org/backup.html) · [WAL persistence](https://sqlite.org/wal.html)

## 6. Acceptance cases to automate

Build these against the normal service/component entry points. The values are deliberate synthetic fixtures except where the design labels a published historical observation. Write small deterministic tests that distinguish the correct calculation from a plausible wrong one.

| Area | Positive case and counterexample |
|---|---|
| **Linked viewports** | Test visible Farms, multiple Farms, filtered-out target, hidden Farms in another group, hidden Farms behind Atlas, an empty group, full layout and Atlas alone. Check selected route, active group, unchanged Atlas extent, unchanged Opportunities sort, single event and persistence after serialise/restore. |
| **Map integrity** | Two farms in the same zone have distinct footprint IDs; a dungeon floor point cannot be projected on the outdoor plane without a registered transform. Compare known anchors, extents, axis orientation, unavailable geometry, true zero and missing overlay values. Prove a different winning route does not generate a false like-for-like zone change. |
| **Cold start** | With no player profile, show sourced farms with requirements. With no yield, show required yield/benchmark; with no market quote, show the route and missing price. Importing a character changes eligibility without hiding the world-wide scanner. |
| **Wall** | Use eight distinct hourly observations with a 100c ask/vendor value. Keep an ordinary high-price control and a one-unit bait listing. For exact-tier history, use consecutive same-method books with 800 → 200 → 750 floor units. Assert the −600/+550 net changes, no claim of a sale, and no refill across a missing middle observation. At 100c ask, a second tier of 105c can contaminate `depth5`; at 106c it cannot. |
| **Book and coverage** | A 12-unit quote can succeed inside a capped book; a 100-unit order with 80 visible units yields cost for 80 and an unpriced shortfall of 20. Reject cross-house/timestamp joins, missing fees misread as zero and item-ID-only quotes presented as suffix-specific. Retain the inference-method boundary on volume charts. |
| **Farms** | Route A yields 12 items per 30 elapsed minutes. B yields 7 per 15. At 1g each with a 5% sale cut and zero other costs, conditional rates are **22g 80s/h** and **26g 60s/h**. Give B a 10-minute approach and a 30-minute session; only one complete B loop fits. Apply per-trip time once. Partition bound loot, uncertain AH sales and rare drops. |
| **Craft batch** | Use the design’s two-tier Wintersbite book. One purchased craft gains **4s 25c** and ten lose **1g 1s 50c**. Owning the first four herbs yields **5s 65c** extra versus selling them raw and buying the vial only for the craft. Test exhausted vendor stock, indivisible bundles, unknown variable-yield probabilities and finite profitable volume before unlock payback. |
| **Transformations** | With the documented Alcaz fixture inputs, retain one fragment and gain **7g 40s** versus the hand-in. After surrendering the box its vendor exit disappears. The soulbound toy has no AH exit. Crates choose one complete bundle, count the introductory bonus once, and keep per-character perk rolls conditional. Writ gates and rewards occupy separate edges. |
| **Holdings** | Synthetic 10,000 units at 1s cost **100g**. One 500-unit sale at 3s and 5% cut records **9g 25s** profit and leaves **9,500** economically held. A repeat export cannot create another sale. Check pre-sale snapshots, later reconciled quantities, unknown-cost lots, partial-fill deposit refunds, matching a manual record, suffix mismatch, binding and uncertain inter-alt transfers. |
| **Character progression** | A second Druid reaching an already earned level-25 class milestone earns no new point. An unearned Alchemy 150 challenge is available; Herbalism 150 provides a gameplay unlock only where evidenced. Reloads and zoning preserve the real login time. Two alts with different Well Rested ranks retain their observed values and get separate projections only where supported. |
| **Addon setup/data** | On temporary Windows trees test path with spaces, product parent vs product root, missing AddOns folder, wrong flavour, ambiguous installs, dirty/unowned target, denied write, rename interruption and rollback. Exercise duplicate imports, delayed metadata, stale/partial bank, unsupported export version, moved folder, missed watcher event and empty-but-complete bag. |
| **Research** | An article recommends the Skulk Rock detour; the linked route gets an exposure marker. Another cave and an instance producing the herb do not inherit its local crowding marker. A buy guide yields a different hypothesis. Unknown reach, absent before-period, article revision and AI outage all preserve dated source links. |
| **Historical replay and price-only false positives** | Replay a rare BoE observation using only evidence available then. A guide published next day cannot explain yesterday’s sale. Keep a distinctive-effect lead even with no comparable trades, but withhold an undervaluation claim. A later item/quest verification can promote the existing lead with its own date. |
| **Operations and archive** | Force import errors, 429 with Retry-After, schema mismatch and expired lease. Assert Console visibility, no duplicate snapshot, bounded logs, SSE cursor replay, bootstrap failure report and clean restart. Test backup/restore across a migration and applying a source-specific expiry policy to cached data on restore. |

Use a Windows CI job for paths, file replacement, clean pnpm/native module install and launcher smoke. Add platform-independent schema/economics tests as useful. Use Vitest, React Testing Library with a simulated DOM, Fastify injection and actual loopback HTTP against the built app, temporary SQLite DBs and an isolated Lua harness. Test doubles can emulate the addon API and events without launching WoW. The release smoke starts on an ephemeral port, waits for health, checks assets/payloads and shuts down its own services.

**Verification boundary.** DOM and SVG assertions verify the routing, geometry data, classes and state; jsdom performs no visual layout. HTTP success cannot validate typography, rendered labels at every viewport size, pointer feel or compatibility in a live WoW client. Record these as visually or in-game unobserved where appropriate. The player can inspect the running candidate during milestone approval without becoming the agent’s regression-test loop. [jsdom limitations](https://github.com/jsdom/jsdom)

## 7. Integration, approval and reporting

1. Branch each task from fetched `origin/development`, using names such as `feat/m1-floor-scanner`. Writers push feature branches and open PRs targeting `development`. Check the base before posting. Public CI runs against synthetic data with minimal permissions and no local-account secrets.
2. A different agent reviews the diff **and its integration base**, tests the named acceptance cases and records the reviewed head SHA, findings, fixes, verdict and checks. When agents use one GitHub account, label this an independent agent review in the PR. Existing rules that require a separate GitHub identity still apply.
3. The integrator updates against current development, resolves conflicts, reruns checks against the result and obtains re-review for material changes. Merge reviewed PRs into development. Confirm the actual remote commit and passing integrated checks. Routine feature integration requires no user sign-off.
4. At a milestone boundary, cut `release/mN` at the **specific integrated SHA** that contains exactly the declared cumulative scope. Open a PR from that frozen candidate to `main`. List included PRs, candidate head, current main base, launch instructions, independent verdict, live/fixture/unknown evidence and material limitations. Development can move forward after the cut.
5. Request explicit user approval for that milestone, scope and SHA. Before promotion verify the release head, current base, mergeability, checks and diff. Use the repository’s permitted normal merge method; when using `gh pr merge`, `--match-head-commit` guards the approved head. It does not guard the base. Recheck the base/diff separately and seek renewed approval for changed candidate contents or materially changed release scope. Never enable main auto-merge while waiting for approval or bypass a protection rule. Prefer a merge commit for promotions if repo settings permit it. [GitHub CLI merge guard](https://cli.github.com/manual/gh_pr_merge) · [Protected branch rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
6. Promote cumulative milestones in order or disclose the complete bundle for approval. Record resulting main SHA and reconcile ancestry with development when required. If access or identity prevents an authorised remote action, retain the reviewed local branch, report the actual blocker and continue independent work.

Each milestone report should fit in one message: **what a player can now do, where to launch it, which commit was reviewed, what the evidence covers, and precisely what is awaiting approval.**
